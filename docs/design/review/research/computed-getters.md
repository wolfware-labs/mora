# Make dot-access honest by meaning, not syntax

No mainstream language guarantees that a field-looking read (`x.Name`) is cheap. Eiffel, C#, Swift, Kotlin, Python and Dart all chose uniform access so suppliers can swap storage for computation without breaking callers, and then each one wrote style guidance asking authors to keep getters cheap, pure and non-throwing. None of them enforces it. The languages that do give a guarantee (Zig, Rust, Go, Odin, Austral) get it by banning computed dot-access outright. That is Mora's Option B, and it is honest, but it costs C#-style ergonomics and the ability to evolve a field into a computed value. The research points to a third path that the systems-language debate has not tried. Databases restrict computed columns with a one-sentence *semantic* rule ("deterministic and precise", "current row only, immutable functions"), and that rule is what lets the engine store or recompute the value without anyone noticing the difference. **Mora should replace the syntactic whitelist with *derived fields*: members declared once, read with field syntax, and defined by a semantic rule ("computed from this object's own state without allocating, mutating, iterating or failing") that the compiler checks through the effect inference it runs on every function. A `stored` variant then moves heavier work from read time to write time, and it is allowed only when every input is privately mutable, so `x.F = v` stays a plain store for every outside caller.** The checks are much the same as Option A's. The difference is how the rule is explained and what it permits. Outside developers get one rule with a visible purpose (the compiler may cache, hoist or debugger-evaluate the value because doing so cannot change behavior), not a list of banned constructs.

## Uniform access bought supplier freedom and left readers with the cost

Uniform access was designed for the supplier, not the reader. Meyer's principle says services should be available "through a uniform notation, which does not betray whether they are implemented through storage or through computation" ([Wikipedia: Uniform access principle](https://en.wikipedia.org/wiki/Uniform_access_principle)). Eiffel's tutorial presents the motivation directly: an account's `balance` can be an attribute or a computed function and clients never change ([Eiffel I2E: Classes](https://account.eiffel.com/doc/eiffel/I2E-_Classes)). C# adopted the same idea as **"smart fields… the calling syntax of fields, and the flexibility of methods"** ([.NET Property Design](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/property)). Kotlin went furthest and has no public fields at all ([Kotlin coding conventions](https://kotlinlang.org/docs/coding-conventions.html)).

Every one of these languages then had to tell authors not to use the freedom too much. Swift's guidelines say why: **"People often assume that property access involves no significant computation, because they have stored properties as a mental model"**, and they ask authors to document any computed property that is not O(1) ([Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/)). PEP 8 warns that "the attribute notation makes the caller believe that access is (relatively) cheap" ([PEP 8](https://peps.python.org/pep-0008/)). Kotlin prefers a property only when the algorithm "does not throw", "is cheap to calculate (or cached on the first run)" and "returns the same result over invocations if the object state hasn't changed" ([Kotlin coding conventions](https://kotlinlang.org/docs/coding-conventions.html)). .NET's CA1024 lists when to use a method instead: when the operation is "perceivably slower than the time that is required to set or get the value of a field", performs a conversion, has an observable side effect, or gives different results on successive calls ([CA1024](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1024)). Taken together, these four ecosystems agree on one informal contract: **cheap, side-effect free, idempotent while state is unchanged, and non-throwing.** Dart is the outlier. It keeps purity and idempotence but says "it's fine for a getter to do significant calculation" ([Effective Dart: Design](https://dart.dev/effective-dart/design)), which shows the contract is a cultural choice, not a law.

No compiler enforces this contract. The .NET analyzers that come closest work on names and shapes: CA1024 actually pushes `Get*` methods *toward* properties, and both CA1024 and CA1819 are **off by default in .NET 10** ([CA1024](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1024); [CA1819](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1819)). Most of the damage comes from that gap. EF Core lazy-loading navigation properties run a database query "the first time a navigation property is touched", which turns a loop into N+1 queries that "look correct" ([Milan Jovanović](https://milanjovanovic.tech/blog/lazy-eager-explicit-loading-ef-core); [JetBrains .NET blog](https://blog.jetbrains.com/dotnet/2023/09/21/eager-lazy-and-explicit-loading-with-entity-framework-core/)). The guilty line "is rarely the line a code reviewer is looking at" ([Hashnode](https://hashnode.com/posts/ef-core-n-1-queries-why-your-api-gets-slower-as-data-grows/6aa933e83deba08c2d56eb35)). Read-only array properties have to copy on every access, and "users won't understand the adverse performance implications", especially when they index the property inside a loop ([CA1819](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1819)). Debuggers silently run getters to fill watch windows, so side-effecting getters change program state when you inspect them ([James Gregory](https://www.jagregory.com/writings/preventing-debugger-property-evaluation-side-effects); [Stefan Gossner](https://blog.stefan-gossner.com/2013/12/04/visual-studio-and-schrdingers-cat-or-why-visual-studio-debugging-is-related-to-quantum-mechanics/)). Caching getters bring their own concurrency bugs. CPython had to remove `cached_property`'s class-wide lock in 3.12 after contention problems, which means the getter can now run twice under a race ([cpython#106292](https://github.com/python/cpython/issues/106292)).

Scala gives Mora the most useful lesson here. Scala 2's convention was that side-effect-free nullary methods are declared without parentheses ([Scala Style Guide](https://docs.scala-lang.org/style/method-invocation.html)). But auto-application let any `def f()` be called as `f`, so the signal was optional and the standard library itself was inconsistent. Scala 3 fixed this by requiring that "the application syntax has to follow exactly the parameter syntax" ([Scala 3: Dropped auto-application](https://docs.scala-lang.org/scala3/reference/dropped-features/auto-apply.html)). That makes the author's chosen signal mandatory at every call site. It still does not check that the signal is true.

## Systems languages bought the guarantee by banning computed dot-access

Systems languages that promise no hidden costs get the guarantee by refusing the feature. Zig states the strongest form: **"If Zig code doesn't look like it's jumping away to call a function, then it isn't"**, and it names D's `@property` as the example it excludes ([Zig overview](https://ziglang.org/learn/overview/)). When Rust discussed properties, the objections split in two. One was visibility: Josh Triplett said "I don't think we should make computed values *look* like fields", and kornel said fields are where "access to them is cheap and deterministic". The other was semantics: a computed result "is not an lvalue", a getter cannot support partial destructuring or split borrows, and `&mut obj.prop` would borrow a temporary ([Rust internals: Idea: Properties](https://internals.rust-lang.org/t/idea-properties/11152)). On the C++ side, N1615 called a property **"behavior that pretends to be state… Behaviour should be visible; state should not"** ([N1615](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2004/n1615.pdf)). Odin ("data should not have 'behaviour'") and Austral ("No implicit function calls") take the same position on philosophical grounds ([Odin FAQ](https://odin-lang.org/docs/faq/); [Austral README](https://github.com/austral/austral/blob/master/README.md)).

These languages replace properties with naming. Go drops the `Get` prefix and writes `Owner()` for field `owner` ([Effective Go](https://go.dev/doc/effective_go#Getters)). Rust drops `get_` and encodes cost in conversion prefixes: **`as_` is free, `to_` is expensive, `into_` consumes** ([Rust API Guidelines](https://rust-lang.github.io/api-guidelines/naming.html)). This only works because the parentheses already say "code runs here", and even then it is a guideline with no lint. Rust's own `Deref` means field-like syntax there can already run user code ([Rust internals](https://internals.rust-lang.org/t/idea-properties/11152)), so only Zig makes the guarantee absolute. Zig also shows a structural trick that matters for Mora. **Functions that allocate must take an allocator parameter** ([Zig overview](https://ziglang.org/learn/overview/)), so the ban on allocation follows from signatures rather than from a rule specific to getters.

The languages that blurred the line through UFCS confirm the risk. D's spec still says property functions are "being reviewed" and "not recommended" more than a decade after DIP23 ([D spec](https://dlang.org/spec/function.html#property-functions)), and a D core contributor later asked what `@property` is for at all, given optional parentheses ([Atila Neves](https://atilaoncode.blog/2018/12/11/what-d-got-wrong/)). Nim avoids a property concept by making every getter a proc call with optional parentheses ([Nim manual](https://nim-lang.org/docs/manual.html#procedures-properties)). That is stable, but `obj.len` then carries no cost information at all.

Carbon is the one systems language that still wants properties, and its restrictions read like a draft of what Mora needs. Chandler Carruth's open issue #1925 expects properties to be "significantly more restricted than fields", with read-only properties modeled "like `let` bindings as R-values" ([carbon-lang #1925](https://github.com/carbon-language/carbon-lang/issues/1925)). Carbon's design document proposes a property only when the member **"is a pure function of the state of the object and executes in an amount of time similar to ordinary member access"**, and it notes that taking an address will differ from a field ([Carbon classes.md](https://github.com/carbon-language/carbon-lang/blob/trunk/docs/design/classes.md#computed-properties)). The issue has no owner and the criterion is guidance only. Rust, C++/CLI and Carbon converge on the same list: R-value semantics, no address-of, purity, member-access cost, and ownership-aware projection instead of copy-out. None of them checks the cost clause mechanically.

## Database computed columns show a semantic rule reads as principled

The most useful precedents come from SQL, not from programming languages, because databases faced the same question and answered it with a property, not a list. SQL Server allows a computed column to be indexed only if it is **deterministic** ("always return the same result for a specified set of inputs") and **precise**. It counts an expression as deterministic only when it has "no system data access or user data access" and "no column reference pulls data from multiple rows" ([SQL Server: Indexes on computed columns](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/indexes-on-computed-columns)). PostgreSQL's rule fits in one sentence: the expression "can only use immutable functions and cannot use subqueries or reference anything other than the current row in any way" ([PostgreSQL: Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html)). Neither rule looks arbitrary, for two reasons. Each clause names a property developers already understand (same inputs give the same output, this row only, no data access). And the restriction visibly serves a purpose: it is what allows the engine to persist or index the value without changing query results. SQL Server even exposes the inferred properties through `COLUMNPROPERTY(..., 'IsDeterministic')` and `'IsPrecise'` ([SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/indexes-on-computed-columns)), so developers can query the classification instead of guessing it.

This is where Option A went wrong in presentation more than in substance. "Field reads, other getters, operators; no loops, calls, allocation, await" reads as an enumerated grammar subset, the kind of rule that seems to change with each release. A semantic restatement can enforce almost the same boundary and still be read as a principle. Effect systems supply the vocabulary. Koka's `total` "signifies the absence of any effect", `div` marks potential non-termination, and `alloc<h>` marks allocation of mutable cells, all inferred without annotations ([Leijen, arXiv 1406.2061](https://arxiv.org/pdf/1406.2061)). Verse separates `<computes>` (no side effects, may not terminate) from `<converges>` (also terminates), and its compiler's effect enum includes `allocates` next to `reads` and `writes` ([Verse API](https://dev.epicgames.com/documentation/en-us/fortnite/verse-api/versedotorg/verse/err); [uLang EEffect](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/VerseCompiler/uLang__EEffect)). Roc infers purity ("a function is effectful if it calls another effectful function") and warns when an effectful function's name lacks the `!` suffix ([Roc langref](https://roc-lang.org/docs/main/langref/functions/)). Roc shows that a cheap, inferred, compiler-checked signal can work in a language aimed at application developers.

Two limits keep this honest. First, **termination is far easier to guarantee than cost.** No production compiler proves O(1). The only real cost-bound inference, RAML's amortized resource analysis, is research tooling for OCaml subsets ([Hoffmann et al., POPL 2017](https://popl17.sigplan.org/details/POPL-2017-papers/56/Towards-Automatic-Resource-Bound-Analysis-for-OCaml)). So Mora's rule has to promise "no iteration and no allocation", which implies time proportional to the expression, not "O(1)". Starlark shows the by-construction version: no recursion and no `while` ([Bazel: Starlark](https://bazel.build/rules/language)). Second, **indirection reopens the loophole.** Koka found that a function stored in a heap cell can recurse without visible recursion ([Koka effects 2013](https://microsoft.com/en-us/research/wp-content/uploads/2016/02/koka-effects-2013.pdf)), and the same applies to virtual dispatch and closures. A Mora derived member may therefore call only statically resolved functions whose inferred effects qualify, or interface members that are themselves declared `derived`.

## Moving cost to write time fits Mora's no-setter model unusually well

Databases also show the second half of the design: one declaration, two storage strategies, same read syntax. In PostgreSQL 18 generated columns are **virtual by default, with `STORED` as a one-word switch**. A stored column "is computed when it is written… and occupies storage as if it were a normal column", while a virtual one "occupies no storage and is computed when it is read" ([PostgreSQL: Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html)). SQL Server's `PERSISTED` "updates them when any other columns on which the computed column depends are updated" ([SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/indexes-on-computed-columns)). Reactive and incremental systems (Jane Street Incremental, Salsa, Svelte `$derived`) also move work off the read path, but they recompute lazily on the next read or on `stabilize`, so a read is not guaranteed to be a plain load ([Jane Street: Incremental](https://blog.janestreet.com/introducing-incremental/); [Salsa book](https://salsa-rs.github.io/salsa/overview.html); [Svelte $derived](https://svelte.dev/docs/svelte/$derived)). The researchers found **no compiled, non-GC language that maintains stored derived fields automatically on mutation**. This is open design space.

Mora's earlier decisions make it a good fit for that space. A stored derived field needs the compiler to see every write to its inputs. Because Mora removed setters, every `x.F = v` is a plain store the compiler can see, and `mut(scope)` limits which code can perform it. If a stored derived field may depend only on fields declared `mut(private)` (or narrower), every write that triggers recomputation is inside the class whose declaration shows the `stored` keyword. Outside callers never see a store that does extra work. That keeps the decision that "`x.F = v` is always a plain store" true at every call site outside the class. The same restriction answers the main objection to write-time maintenance, that it moves hidden cost from reads to writes. The research notes put it this way: write-time cost is acceptable "if the rule is visible in the declaration (as `STORED` is in SQL)", and the `mut(private)` rule ensures the only people who pay it are the people reading that declaration.

Each strategy has an ARC and memory profile, and the rule has to cover them. A virtual derived value of value type (`bool`, `decimal`) costs nothing beyond the field loads it performs. Returning a reference-typed field through a virtual derived member costs what reading that field costs (a borrow, or a retain if the caller keeps it), which is the same as a field read. A *new* reference-typed value, such as a concatenated `FullName` string, must allocate, so it cannot be virtual. It has to be `stored` (paid once per write, kept in memory per instance) or a method. A stored derived field adds a slot to every instance, releases the old value on recompute, and must not reference `this`, so it cannot create a retain cycle with its owner. With unique ownership, reading a stored derived field is a borrow, and the value can never be moved out. Lazy caching (Swift `lazy`, Python `cached_property`, Kotlin `by lazy`) should be left out entirely. It adds a "computed?" flag, raises thread-safety choices that Swift leaves unsafe and Kotlin pays for with synchronization, and goes stale on mutation unless someone invalidates it ([Python functools](https://docs.python.org/3/library/functools.html#functools.cached_property); [Kotlin lazy](https://kotlinlang.org/docs/delegated-properties.html#lazy-properties)).

## Candidate designs for Mora

All candidates assume Mora's existing model (state is fields, `mut(scope)` controls writes, behavior is methods, no setters). The running example is a bank account.

### 1. Derived fields: virtual by default, `stored` opt-in (recommended)

```mora
class Account {
    public mut(private) decimal Balance;
    public mut(private) decimal Overdraft;
    public mut(private) string First;
    public mut(private) string Last;

    public derived bool IsOverdrawn => Balance < 0;                     // virtual: computed on read
    public derived decimal Available => Balance + Overdraft;            // virtual
    public derived stored string FullName => $"{First} {Last}";         // stored: recomputed when First/Last change

    public decimal ProjectedInterest(Rate r) => /* loops, calls: a method */;
}

if (acct.IsOverdrawn) { ... }   // reads like a field, costs like a few field loads
```

**Rule an outside developer reads:** "A derived field is a value computed only from this object's own data. It cannot allocate, mutate, loop or fail, so the compiler may compute it on read or store it, and you cannot tell the difference." The `stored` form adds: "stored derived fields are recomputed whenever the private fields they depend on change; they may allocate, because that happens at write time." **Guarantees:** a virtual read costs a bounded number of loads and arithmetic operations, with no allocation, no ARC traffic beyond what reading the source fields would cause, no side effects, and the same result until a dependency changes. A stored read is one load. Because the value is deterministic, the compiler can safely CSE or hoist it out of loops, and the debugger can evaluate it without the C# func-eval hazard ([Mike Stall, func-eval](https://learn.microsoft.com/en-us/archive/blogs/jmstall/what-does-a-debugger-author-need-to-do-to-support-func-eval)). Changing a public field into a derived field keeps every call site source-compatible, so Meyer's evolution argument survives. **Costs and pitfalls:** `stored` adds memory per instance and makes writes inside the class more expensive. Stored inputs must be `mut(private)` or narrower, and a stored value may read only the object's own fields, not fields of child objects, because a child's writes cannot trigger recomputation (PostgreSQL's "current row only"). Taking a mutable `ref` to a stored input must either be forbidden or recompute at the end of the borrow, in the style of Swift's yielding `mutate` ([SE-0474](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0474-yielding-accessors.md)). Derived fields cannot reference other *stored* derived fields, which avoids ordering chains, as PostgreSQL does. Taking the address of a virtual derived field is an error, as in C++/CLI ([N1600](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2004/n1600.html)). Floating-point results are deterministic in a compiled language with fixed semantics, so SQL Server's "precise" clause does not apply unless Mora allows fast-math reassociation. **Precedent:** PostgreSQL 18 virtual/stored generated columns, SQL Server `PERSISTED`, Carbon's "pure function of object state" criterion. The compiled-language version, including write-site recomputation, is novel.

### 2. Effect-checked getters (the semantic restatement of Option A)

```mora
public bool IsOverdrawn => Balance < 0;
public decimal Available => Balance + Math.Max(Overdraft, 0);   // OK: Math.Max is inferred pure, non-allocating, total
public int LineCount => Lines.Count;                            // OK: Count is itself a getter
public decimal Total => Lines.Sum(l => l.Amount);
// error: getter 'Total' iterates (via Enumerable.Sum, line 12).
//        Getters must finish without looping or allocating. Make it a method: Total().
```

**Rule:** "A getter may do anything a pure, non-allocating, non-looping function may do; the compiler infers those properties for every function and tells you which call broke them." **Guarantees:** the same read-time guarantees as virtual derived fields. It also allows calls to helper functions that Option A would ban, as long as their inferred effects qualify. That turns a blacklist of constructs into a reusable property, shown in IDE hovers the way SQL Server reports `IsDeterministic`. **Costs and pitfalls:** effects become part of a library's public contract. A library that changes `Math.Max` to allocate breaks downstream getters, so semver tooling has to track inferred effects (Roc and Koka infer effects, but neither ships a large binary-library ecosystem). Virtual and interface calls need declared effects. Recursion and higher-order arguments need either a termination analysis or a flat ban, and Koka's experience shows a ban is the realistic choice. Recoverable errors must be excluded, but whether arithmetic traps (overflow, division by zero) count as "failure" needs a decision. Treating them as bugs, not effects, keeps `Available` legal. **Precedent:** Koka `total`/`div`/`alloc`, Verse `computes`/`converges`/`allocates`, Roc purity inference, SPARK `Global => null`, Solidity `view`/`pure`. This is Candidate 1 without the `stored` form, and it is the fallback if write-time maintenance proves too complex for v1.

### 3. Projections only: dot means "stored data, possibly reached through other stored data"

```mora
public derived string City => Address.City;           // OK: a path into stored state
public derived bool IsOverdrawn => Balance < 0;       // error: computes a new value; use IsOverdrawn()
public derived byte Flags => Packed.Low;              // OK: bit-field view
```

**Rule:** "`x.Name` always names stored data; anything that computes is a method." **Guarantees:** a read is a chain of loads, yielded as a borrow with no retain and no copy, which suits ARC with unique ownership very well. It also supports encapsulated layout changes (bit packing, flattening), Carbon's stated use case ([carbon-lang #1925](https://github.com/carbon-language/carbon-lang/issues/1925)). **Costs and pitfalls:** it does not solve the motivating case, since `IsOverdrawn` is still a method. Projections through child objects can dangle if the child is replaced during the borrow, so they need borrow-scope rules. The ergonomic gain over plain public fields is small. **Precedent:** Hylo projections and subscripts ([Hylo tour](https://docs.hylo-lang.org/language-tour/subscripts)), Swift yielding accessors (SE-0474), Rust field projection ([RFC PR 3318](https://github.com/rust-lang/rfcs/pull/3318)).

### 4. Option B plus a compiler-checked call shape (no getters)

```mora
public bool IsOverdrawn() => Balance < 0;
public string ToDisplayName() => $"{First} {Last}";   // naming convention: To* allocates
if (acct.IsOverdrawn()) { ... }
```

**Rule:** "Dot without parentheses is always a field load; parentheses always mean code runs." **Guarantees:** the strongest and simplest guarantee, Zig-grade honesty, with no new concepts and nothing to invalidate. **Costs and pitfalls:** C# developers lose the `x.IsOverdrawn` idiom, and turning a field into a computed value breaks every caller, which is the evolvability that uniform access exists to protect. Cost classes inside the parentheses depend on naming, and Rust's `as_`/`to_` convention is guidance with no lint ([Rust API Guidelines](https://rust-lang.github.io/api-guidelines/naming.html)). Mora could add a Roc-style check (warn when a `To*`-free name allocates), but that is another heuristic. **Precedent:** Rust, Go, Zig, Odin, Java records ([JEP 395](https://openjdk.org/jeps/395)), and Scala 3's rule that call shape matches declaration.

### 5. Inferred call shape: the compiler decides whether parentheses are required

```mora
public bool IsOverdrawn => Balance < 0;                 // inferred cheap: callers write acct.IsOverdrawn
public decimal Total => Lines.Sum(l => l.Amount);       // inferred iterating: callers must write acct.Total()
```

**Rule:** "Members the compiler proves cheap read like fields; everything else needs parentheses." **Guarantees:** call sites are always honest, and authors never write an annotation. **Costs and pitfalls:** editing a body changes the required syntax at every call site, across packages, so the API shape depends on implementation details. That is exactly what uniform access was meant to prevent, and it is worse than either B or A for library authors. It survives only as an IDE feature: inferred cost shown as an inlay hint on method calls. **Precedent:** SQL Server's inferred `IsDeterministic`/`IsPrecise`, and Roc's inferred purity with a naming check. Including it here as a design is novel, but it is not recommended.

| Candidate | `x.IsOverdrawn` legal? | Read cost guarantee | Write stays plain store outside class | New concepts | Main risk |
|---|---|---|---|---|---|
| 1. Derived fields (virtual + stored) | Yes | Loads + arithmetic, or one load | Yes (`mut(private)` inputs) | `derived`, `stored` | Write-site recompute complexity |
| 2. Effect-checked getters | Yes | Loads + arithmetic + pure calls | Yes (no stored form) | Inferred effects | Effects leak into library contracts |
| 3. Projections only | No | Chain of loads, borrow | Yes | Projection | Does not cover computed booleans |
| 4. Option B + call shape | No | Field load always | Yes | None | Ergonomics, field evolution breaks callers |
| 5. Inferred call shape | Sometimes | Proven by compiler | Yes | None visible | Unstable API surface |

### Ranked recommendation

**First, Candidate 1 (derived fields), built on Candidate 2's effect inference.** It is the only design that keeps C#-style `x.IsOverdrawn`, keeps "`x.F = v` is a plain store" true for every outside caller, and gives a rule whose justification is visible. The restriction exists because the compiler is free to store, cache, hoist or debugger-evaluate the value, just as SQL's determinism rule exists because the engine may persist or index the column. The checks are close to Option A's. The difference is that the rule names properties instead of constructs, allows calls that qualify, and reports violations as "this call allocates" instead of "calls are not allowed here". The `derived` keyword also marks the member as a different kind of thing from a method, so `public derived bool IsOverdrawn` tells a reader something a bare `=>` does not. Make `stored` explicit rather than letting the compiler or PGO choose. Automatic choice changes object layout and memory, and choices with hidden costs are what Mora is trying to avoid.

**Second, Candidate 2 alone,** if write-time maintenance is out of scope for v1. It ships the same read-side rule, and `stored` can be added later without breaking source, because virtual and stored reads are indistinguishable by construction. **Third, Candidate 4 (Option B),** which is the safe default if effect inference is not on the roadmap. It is honest and proven, and it costs ergonomics, not guarantees. **Fourth, Candidate 3,** which is worth adopting as a later *addition* for layout encapsulation but does not answer the question. **Last, Candidate 5,** which belongs in the IDE, not the language. Two decisions in Candidate 1 remain open and need prototyping: whether arithmetic traps count as "failing", and how inferred effects are versioned across package boundaries. The researchers found no precedent for the second in a compiled language with binary libraries.

## Conclusion

The field-versus-getter debate has usually been framed as syntax: parentheses or no parentheses, uniform access or visible calls. The evidence shows that framing fails both ways. Languages that allow getters cannot keep them cheap with guidance, and languages that ban them give up evolvability to stay honest. Databases solved the same problem by attaching meaning to the declaration, not the call site, and by tying the restriction to something the system actually does with the value. Mora is unusually well placed to use that solution, because it already removed setters and scoped writes with `mut`. Those decisions mean the compiler sees every write to a derived field's inputs, which is the condition for write-time maintenance that general-purpose languages have never met.

What the designer should take from this is that "looks arbitrary" is a property of the explanation as much as of the boundary. A whitelist and an effect rule can reject almost the same programs. One reads as a list of prohibitions, and the other reads as a promise ("same answer, no work, cache it if you like") that developers can use when reasoning about their code. The remaining risk is not conceptual but ecosystem-level: once inferred effects decide what a derived field may call, those effects become part of every library's contract, and Mora will need versioning tooling for them before it has a large package ecosystem.
